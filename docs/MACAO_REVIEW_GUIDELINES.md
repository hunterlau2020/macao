# MACAO 评审方法论

> **版本**：v1.0（2026-08-25）
> **状态**：草案，供各角色评审 PRD/SRS 等设计文档、以及后续 Adapter / Workflow Engine 代码时使用
> **改编自**：`docs/REVIEW_METHODOLOGY.md`（Washdb 项目财务数据评审方法论 v2.2，第三方项目文档）
> **上位准则**：`docs/MACAO_PRD_v2.md`（v2.0 权威基准文档）

本方法论保留原方法论的核心闭环，把评审对象从"财务数据 Loader/Pipeline"替换为"MACAO 的设计文档、协议 Schema、Adapter/Workflow 代码与状态机行为"：

```text
声明 → 文档/代码/产物 → 场景重放 → 反例与失败路径 → 权威基准（PRD v2.0）
```

任何"对齐"或"通过"结论都必须指明评审对象、对应 commit、证据、适用门禁与未决风险。作者自述、单一 happy-path 示例、reviewer 投票均不能代替证据。

---

## 1. 目的、边界与文档分工

### 1.1 目的

1. 防止把"文字上提到了" "有个例子" "看起来一致" 与"可被唯一、机器可验证地推导出同一行为"混为一谈；
2. 防止只看标题、目录或摘要文档而忽略正文与权威基准的偏差；
3. 覆盖正常路径、异常路径（超时/弃权/崩溃/冲突）、历史文档遗留内容、字段与术语一致性；
4. 使结论可复现、可反驳，并可追溯到具体文件路径、行号与 commit；
5. 让 reviewer 自身的遗漏、分歧与修正同样进入审计记录（`docs/reviews/`）。

### 1.2 适用范围按对象裁剪

| 对象 | 最低适用章节 |
|---|---|
| PRD / SRS / 执行摘要等设计文档的跨文档对齐评审（当前阶段） | §1–§6、§9、§11 |
| `.dev.yml` / `.review.yml` / `vote_result.json` / AEP 消息 Schema | 全文，重点 §4、§6、§7 |
| Adapter（Claude Code / Codex / Kimi）与 Workflow Engine 代码 | 全文 |
| 一次性研究性文档草稿或纯格式修订 | §1、§2、§9（DOC-ALIGNED 即可，无需虚构 CODE/SIM 证据） |

MACAO 现阶段（docs 对齐评审）不涉及金融语义、SEC、DuckDB 等原方法论 §5/§7/§12/§13 的内容，故本改编版不予保留；进入代码与联调阶段后，应按 §8 补充针对 PTY/进程/并发的对应章节。

### 1.3 稳定规范与实时状态分离

本文件只保存稳定评审标准。以下内容必须另存，不得写入本文件正文：

```text
docs/reviews/STATUS.md                              当前文档版本/门禁状态（如需要）
docs/reviews/<yyyy-MM-dd>-review-result-<mid>-<reviewer>.md   单次评审结论
docs/reviews/meta_<yyyy-mm>.md                       reviewer 连续漏审复盘（如需要）
```

`<mid>` 使用被评审内容对应的短 commit SHA；`<reviewer>` 使用执行评审的角色/模型标识（如 `claude`、`codex`）。

## 2. 四级结论与四类 Phase Gate（改编）

### 2.1 四级结论

| 级别 | 结论 | 最低条件 | 允许动作 |
|---|---|---|---|
| **L1 DOC-ALIGNED** | 设计文档之间、与权威基准之间一致 | 四份文档字段/术语/勾选状态可用同一张对照表逐条核验；所有 YAML/JSON 示例是合法可解析格式；确定性用语（99%/100%）已标注"目标"而非既成事实 | 允许据此开始编码/PoC |
| **L2 SPEC-CODE-ALIGNED** | 代码实现与 PRD 规范一致 | L1 + Adapter/Engine 静态检查、单元测试通过，字段命名与 Schema 逐字段对应 | 允许继续开发，不代表端到端行为已验证 |
| **L3 SCENARIO-VERIFIED** | 关键场景可从文档或系统唯一推出预期结果 | L2 + 全同意/1:1 僵局/超时/弃权/崩溃恢复/返工循环等场景均有可复现推演或测试证据 | 具备进入联调/下游依赖资格 |
| **L4 RELEASE-READY** | 可对外演示/发布 | L3 + 人工接管路径实机演练、回归无 P0/P1、用户手册齐备 | 允许正式发布 |

`UNKNOWN` 不等于 PASS；局部对齐不得外推为整份文档体系对齐。

### 2.2 Phase Gate

| 门禁 | 含义 | 条件 |
|---|---|---|
| **PG-0** | 允许开始编码/PoC | L1 |
| **PG-1** | 当前阶段内部验收 | L2；P0/P1 为零 |
| **PG-2** | 允许下游模块/团队依赖该规范 | PG-1 + 接口稳定 + 消费方场景测试 |
| **PG-3** | 生产发布/对外演示 | L4 |

**当前状态**：四份文档尚有 P0 级冲突未闭环（见最近一次 `docs/reviews/*-claude.md` / `*-codex.md`），处于 PG-0 与 PG-1 之间——可以开始 PoC 探索，但不应把四份文档作为可直接实现的完整规格。

## 3. 证据类型与验证状态

### 3.1 证据类型

| 类型 | 含义 |
|---|---|
| **DOC** | 文档正文、表格、示例的直接引用 |
| **SPEC** | 规范自身的内部一致性（同一份文档内，伪代码/表格/正文是否互相矛盾） |
| **CODE** | reviewer 静态检查指定 commit 的 Adapter/Engine 代码 |
| **SIM** | reviewer 手工或脚本重放的场景推演（例如按状态转换表逐步推导某个具体输入的结果） |
| **TEST** | 正常、边界、失败与恢复路径的自动化测试 |
| **OPS** | PTY 进程管理、并发、崩溃恢复、agmsg 队列演练 |

### 3.2 验证状态

```text
VERIFIED
PARTIALLY_VERIFIED
CLAIM_ONLY
UNKNOWN
CONTRADICTED
NOT_APPLICABLE
```

### 3.3 证据最低要求

- L1：DOC/SPEC 为 VERIFIED（即：给出确切文件路径 + 行号，且交叉引用不矛盾）；
- L2：CODE 为 VERIFIED；
- L3：SIM/TEST 覆盖所有适用 P0/P1 场景且为 VERIFIED；
- L4：OPS 为 VERIFIED，且完成用户可见的人工接管演练。

"读了标题" "作者说已完成" 不能使 DOC 证据达到 VERIFIED；必须能指出具体行号或字段。

## 4. 声明验证矩阵（MACAO 专用）

作者/文档中的每个强声明都必须转成可核验的检查项：

| 声明 | 必须验证 |
|---|---|
| "显式信号优先，100%/99% 可信" | Layer 2/3 的代码或伪代码是否真的只产生日志/预警，不直接返回业务状态；正文与伪代码是否一致 |
| "N/3 多数投票" | 给出 2/3/N reviewer 配置下：全同意、1:1、1 弃权、全弃权、1 超时 等场景的显式决策表，且与流程图/状态表/降级策略描述一致 |
| "所有状态转换可 git log 审计" | 产物文件路径是否按 checkpoint/round 区分或原子提交；同名文件被覆盖时审计链是否仍完整 |
| "review_context 完整，reviewer 一眼看懂" | Reviewer 标准工作流读取的字段名/文件（如 `/tmp/code_changes.patch`）是否与 MACAO 实际发送的字段名/格式一致 |
| "checklist 全部 `[x]` / 已完成" | 是否有可核验的完成证据（PoC 结果、测试记录），而不是把"计划做"标记为"已做" |
| "AEP 定义 N 种消息类型" | 文档中出现"完整格式""详细格式"等措辞时，是否与实际给出详细 Schema 的消息类型数一致 |
| 同一实体的字段命名（如 checkpoint 标识） | 是否在 `.dev.yml` / `.review.yml` / `vote_result.json` / AEP payload / 摘要示例 中使用同一字段名；如故意分层命名，是否有文字说明原因 |

## 5. 术语与产物一致性（唯一权威表）

必须维护一张"产物 — 生成者 — 路径 — 格式 — 关键字段 — 版本/保留策略"的唯一对照表（建议直接放入 PRD 附录），四份文档中的所有示例字段必须能对照该表逐字段核验。禁止：

- 用不同名词描述同一决策结果（如 `REJECTED` vs `REWORK_REQUIRED` vs `REWORK`）；
- 把 MACAO 生成的 JSON 产物统称为"CLI 生成的 .yml 文件"；
- 摘要/改进说明文档中的示例字段名与权威基准文档中的 Schema 字段名不一致（如 `checkpoint` vs `checkpoint_ref` vs `checkpoint_id`）。

## 6. 反例与边界场景库（MACAO 专用）

评审状态机、投票规则、Context 协议时，至少应对照以下场景逐一推演，并记录预期结果是否能从文档唯一推出：

```text
2-reviewer 全部弃权
2-reviewer 1 超时 + 1 批准
2-reviewer 1 批准 + 1 反对（1:1 僵局）
3-reviewer 1:1:1 三方不一致
Reviewer 进程崩溃后重启并重复提交投票
同一 checkpoint 收到两份同 reviewer_id 的 .review.yml（重试去重）
.dev.yml 缺少必需字段但 signal=EXPLICIT
第二轮返工时 .review.yml 是否覆盖第一轮记录
人工接管超时后系统的默认动作（是否静默按高置信度状态继续）
Git 冲突导致 checkpoint 引用的 commit 与工作区不一致
review_context 中的 diff/patch 字段与 Reviewer 工作流期望的载体（命令/文件/ref）不一致
```

每个场景应保存来源文档/行号、预期结果、实际能否唯一推导、以及验证该场景所需的最小测试或推演步骤。

## 7. 失败路径与恢复测试隔离规则（进入代码阶段后适用）

1. 使用临时工作区（临时 git repo / `.macao/` 沙箱），不得污染真实项目仓库；
2. 不得使用真实 CLI 厂商账号额度进行破坏性测试；
3. 优先使用 fault-injection（模拟 PTY 断开、模拟消息丢失），避免真实 `kill -9` Adapter 进程作为唯一验证手段；
4. 测试结束需验证 `.macao/` 临时文件、锁与残留进程已清理；
5. 崩溃恢复类测试必须验证"重启后是否重复投票/重复生成产物"。

## 8. Known issues、严重级与分歧仲裁

沿用原方法论的核心原则：

- **P0/P1**：PG-1、PG-2、PG-3 不可豁免；必须记录 issue_id、evidence、owner、due_date、resolution_commit、status；
- **P2/P3**：可在明确风险接受后延期，但延期不等于"没问题"；
- **UNKNOWN**：若可能影响状态机行为、投票结果或审计完整性，按 P0/P1 处理直到澄清；
- **真理不等于投票**：每项 REJECT/P0/P1 必须附可复现证据（文件路径 + 行号 + 具体矛盾点），不以 reviewer 人数或身份代替证据；
- **沉默 ≠ 同意**：未表态的 reviewer 不计入"多数"；
- **审计相关的结构性变更**（产物路径、状态枚举、投票公式）应要求多 reviewer 共识而非简单多数表决。

## 9. 文档评审专用自审 Checklist（改编自原 §18 A–D 模式）

同一 reviewer 连续几轮对**同一类盲点**漏审时，必须显式登记（登记到当次 review 文件 §0）并激活对应 checklist 项。以下是文档对齐评审场景下已反复出现的通用盲点：

| # | 漏审模式 | 典型后果 |
|---|---|---|
| **A** | 字段声明位置 vs 代码/伪代码实际读取位置不一致（如字段声明在嵌套结构下，伪代码却从根路径读取） | 实现按伪代码编写后，字段永远读不到，运行时静默失败 |
| **B** | checklist `[x]` ≠ 已有完成证据 | 把"计划要做"误当作"已完成"合入决策 |
| **C** | 确定性语言（100%/99%/"无条件可信"）未标注"设计目标"还是"已验证事实" | 读者/实现者把设计目标当作已验证行为直接生产使用 |
| **D** | 代码块格式不可执行（JSON 内嵌 `#` 注释、字段名与正式 Schema 不一致的"示意"代码） | 实现者按示例直接照抄，产生无法解析的产物 |

强制自检（文档评审每轮必查）：

```text
□ 1. 字段名 vs 实际读取路径是否一致？（正文 Schema vs 伪代码/示例）
□ 2. 每一处 [x] / "已完成" / "✅" 是否有对应证据，而非计划？
□ 3. 每一处 "100%" "99%+" "无条件" 等确定性用语是否标注了目标/待验证？
□ 4. 每一段声称是 YAML/JSON 的代码块是否真的能被解析（无非法注释、字段名与 Schema 一致）？
□ 5. 每个 REJECT/P0/P1 是否给出了可复现的文件路径 + 行号证据？
```

## 10. 单次评审交付物模板

`docs/reviews/<yyyy-MM-dd>-review-result-<mid>-<reviewer>.md` 至少包含：

```markdown
# <评审对象> 对齐/评审结论

- 评审日期 / 评审范围 / 对齐或评审基准
- 结论（L1–L4，或 PG-0–PG-3 判定）
## 已对齐 / 已确认项
## P0：必须先解决
## P1：发布/进入下一阶段前应修正
## P2/P3：可延期但需登记
## 交叉文档需做的文字修订
## 建议的闭环顺序与验收标准
## Reviewer 自审记录（如有连续漏审，登记于此）
```

agmsg / 简报中只发送结论、1–2 个 blocker 与详细报告路径；完整证据保留在报告文件中。

## 11. 生效与修订

本方法论的修改必须：

1. 指明触发问题（例如某类漏审导致了什么后果）；
2. 提供至少一个正例和一个反例；
3. 不得把当前项目的临时状态（某次评审结论、当前 P0 列表）写入本文件正文，应写入 `docs/reviews/`；
4. 检查代码块可执行性与 Markdown 完整性；
5. 由至少两名 reviewer（或两次独立评审）审阅后生效。
