# MACAO 评审方法论

> **版本**：v1.1（2026-09-08）
> **状态**：生效规范，供各角色评审 PRD/SRS/架构等设计文档、以及 Adapter / Workflow Engine / CLI 代码时使用
> **改编自**：《Washdb 项目财务数据评审方法论 v2.2》（存放在 `docs/reference/REVIEW_METHODOLOGY.md`，仅作方法来源与基准架构标注）
> **上位准则**：`docs/MACAO_PRD_v2.md`（权威基准文档）

本方法论保留原方法论的核心闭环，把评审对象从"财务数据 Loader/Pipeline"替换为"MACAO 的设计文档、协议 Schema、Adapter/Workflow 代码与状态机行为"：

```text
声明 → 文档/代码/产物 → 场景重放 → 反例与失败路径 → 权威基准（PRD v2.0）
```

任何"对齐"或"通过"结论都必须指明评审对象、对应 commit、证据、适用门禁与未决风险。作者自述、单一 happy-path 示例、reviewer 投票均不能代替证据。

---

## 1. 目的、边界与文档分工

### 1.1 目的

1. 防止把"文字上提到了" "有个例子" "看起来一致" 与"可被唯一、机器可验证地推导出同一行为"混为一谈；
2. 防止只看标题、目录或摘要文档而忽略正文与权威基准的偏差；
3. 覆盖正常路径、异常路径（超时/弃权/崩溃/冲突）、历史文档遗留内容、字段与术语一致性；
4. 使结论可复现、可反驳，并可追溯到具体文件路径、行号与 commit；
5. 让 reviewer 自身的遗漏、分歧与修正同样进入审计记录（`docs/reviews/`）。

### 1.2 适用范围按对象裁剪

| 对象 | 最低适用章节 |
|---|---|
| PRD / SRS / 执行摘要等设计文档的跨文档对齐评审（当前阶段） | §1–§6、§9、§11 |
| `.dev.yml` / `.review.yml` / `vote_result.json` / AEP 消息 Schema | 全文，重点 §4、§6、§7 |
| Adapter（Claude Code / Codex / Kimi）与 Workflow Engine 代码 | 全文 |
| 一次性研究性文档草稿或纯格式修订 | §1、§2、§9（DOC-ALIGNED 即可，无需虚构 CODE/SIM 证据） |

MACAO 现阶段（docs 对齐评审）不涉及金融语义、SEC、DuckDB 等原方法论 §5/§7/§12/§13 的内容，故本改编版不予保留；进入代码与联调阶段后，应按 §8 补充针对 PTY/进程/并发的对应章节。

### 1.3 稳定规范与实时状态分离

本文件只保存稳定评审标准。以下内容必须另存，不得写入本文件正文：

```text
docs/reviews/STATUS.md                                        当前文档版本/门禁状态（如需要）
docs/reviews/<yyyy-MM-dd>-review-request-<mid>[-<topic>].md   评审申请文件（含 commit ID，不可变归档，防覆盖）
docs/reviews/<yyyy-MM-dd>-review-result-<mid>-<reviewer>.md   单次评审结论
docs/reviews/meta_<yyyy-mm>.md                                reviewer 连续漏审复盘（如需要）
```

`<mid>` 使用被评审内容对应的短 commit SHA（如 `4027cce`、`6e35a71`）；`<reviewer>` 使用执行评审的角色/模型标识（如 `claude`、`codex`、`grok`、`qwen`）。**每次评审申请必须在文件名中携带 `<mid>`**，严禁跨轮次同名覆盖。

## 2. 四级结论与四类 Phase Gate（改编）

### 2.1 四级结论

| 级别 | 结论 | 最低条件 | 允许动作 |
|---|---|---|---|
| **L1 DOC-ALIGNED** | 设计文档之间、与权威基准之间一致 | 四份文档字段/术语/勾选状态可用同一张对照表逐条核验；所有 YAML/JSON 示例是合法可解析格式；确定性用语（99%/100%）已标注"目标"而非既成事实 | 允许据此开始编码/PoC |
| **L2 SPEC-CODE-ALIGNED** | 代码实现与 PRD 规范一致 | L1 + Adapter/Engine 静态检查、单元测试通过，字段命名与 Schema 逐字段对应 | 允许继续开发，不代表端到端行为已验证 |
| **L3 SCENARIO-VERIFIED** | 关键场景可从文档或系统唯一推出预期结果 | L2 + 全同意/1:1 僵局/超时/弃权/崩溃恢复/返工循环等场景均有可复现推演或测试证据 | 具备进入联调/下游依赖资格 |
| **L4 RELEASE-READY** | 可对外演示/发布 | L3 + 人工接管路径实机演练、回归无 P0/P1、用户手册齐备 | 允许正式发布 |

`UNKNOWN` 不等于 PASS；局部对齐不得外推为整份文档体系对齐。

### 2.2 Phase Gate

| 门禁 | 含义 | 条件 |
|---|---|---|
| **PG-0** | 允许开始编码/PoC | L1 |
| **PG-1** | 当前阶段内部验收 | L2；P0/P1 为零 |
| **PG-2** | 允许下游模块/团队依赖该规范 | PG-1 + 接口稳定 + 消费方场景测试 |
| **PG-3** | 生产发布/对外演示 | L4 |

**当前状态**：实时门禁状态不记录在本文件内（见本文件"实时状态必须另存"规则），统一维护于 `docs/reviews/STATUS.md`。

*注：关于 PG-1 条件与源方法论的差异说明：Washdb 的 PG-1 要求「当前 Phase L3」，而 MACAO 明确收敛为 L2（规范与实现对齐且 P0/P1 为零），因关键跨组件场景推演与端到端集成测试（L3 SCENARIO-VERIFIED）统一与 PG-2（允许下游依赖）伴随授予。*

## 3. 证据类型与验证状态

### 3.1 证据类型

| 类型 | 含义 |
|---|---|
| **DOC** | 文档正文、表格、示例的直接引用 |
| **SPEC** | 规范自身的内部一致性（同一份文档内，伪代码/表格/正文是否互相矛盾） |
| **CODE** | reviewer 静态检查指定 commit 的 Adapter/Engine 代码 |
| **SIM** | reviewer 手工或脚本重放的场景推演（例如按状态转换表逐步推导某个具体输入的结果） |
| **TEST** | 正常、边界、失败与恢复路径的自动化测试 |
| **OPS** | PTY 进程管理、并发、崩溃恢复、agmsg 队列演练 |

### 3.2 验证状态

```text
VERIFIED
PARTIALLY_VERIFIED
CLAIM_ONLY
UNKNOWN
CONTRADICTED
NOT_APPLICABLE
```

### 3.3 证据最低要求

- L1：DOC/SPEC 为 VERIFIED（即：给出确切文件路径 + 行号，且交叉引用不矛盾）；
- L2：CODE 为 VERIFIED；
- L3：SIM/TEST 覆盖所有适用 P0/P1 场景且为 VERIFIED；
- L4：OPS 为 VERIFIED，且完成用户可见的人工接管演练。

"读了标题" "作者说已完成" 不能使 DOC 证据达到 VERIFIED；必须能指出具体行号或字段。

### 3.4 验证命令的作用域

每条 TEST / OPS 证据必须声明其**参照系**，且参照系必须与结论的适用范围一致。结论说的是哪个对象，命令就必须作用在哪个对象上：

| 结论谈的是 | 必须的参照系 | 常见的错误参照系 |
|---|---|---|
| 某个 commit 是否洁净 | `git show --check <full_sha>` | `git diff --check`（检工作树，提交后恒 rc=0，无信息量） |
| 某个 commit 的测试是否全绿 | 该 commit 的干净 checkout / worktree | 含未提交改动或残留产物的工作树 |
| 在任意干净环境可用 | 受控的最小 PATH / 容器隔离环境 | reviewer 本地预装了特定工具的开发机 |
| 跨平台可用 | 各目标平台各跑一次；无实机条件时明确降为 CODE 推理 | 单一平台实跑后直接外推全平台 |
| 安装后可用 | 干净 venv 中的 `pip install` 产物 | 源码树挂载 + `PYTHONPATH=src` |
| 负向防御分支有效阻断 | 断言非零退出码（`assertNotEqual(exit_code, 0)`）与错误日志 | 仅断言函数未抛未捕获异常或退出码为 0 |

作者与 reviewer 双方均须自检。凡参照系与结论不一致的绿灯，验证状态最高只能记为 `PARTIALLY_VERIFIED`，并注明其成立的前提约束；作者在申请文档中给出的验证命令不构成 reviewer 免于自检参照系的理由。

### 3.5 复现证据的归档

任何用于支撑 P0/P1 缺陷定级或 SIM/TEST 状态判定的验证脚本，必须随报告归档，不得只存在于终端滚屏或临时目录（如 `/tmp`、会话 scratchpad）：

- **归档位置**：`docs/reviews/evidence/<yyyy-MM-dd>-<short_commit>-<reviewer>/`；
- **单文件脚本**：可内联在评审报告附录的「复现脚本与命令」章节中，但必须是**完整且可直接粘贴执行**的代码，严禁省略为难以复跑的代码片段；
- **元数据登记**：每个脚本均须登记：所验证的 `issue_id`、执行时的完整 commit SHA、依赖的外部前提（网络、已安装的 CLI 工具、操作系统平台），以及**最后一次实际执行的日期与时间**；
- **环境隔离要求**：脚本若涉及临时工作区或状态库，必须由脚本自身通过 `tempfile.mkdtemp()` 动态创建并负责清理，不得依赖 reviewer 手工准备的本地隐式状态。

「在报告里贴出执行日志输出」不等于证据可复现。任何复审者均应能仅凭归档脚本重放并证伪该发现。

## 4. 声明验证矩阵（MACAO 专用）

作者/文档中的每个强声明都必须转成可核验的检查项：

| 声明 | 必须验证 |
|---|---|
| "显式信号优先，100%/99% 可信" | Layer 2/3 的代码或伪代码是否真的只产生日志/预警，不直接返回业务状态；正文与伪代码是否一致 |
| "N/3 多数投票" | 给出 2/3/N reviewer 配置下：全同意、1:1、1 弃权、全弃权、1 超时 等场景的显式决策表，且与流程图/状态表/降级策略描述一致 |
| "所有状态转换可 git log 审计" | 产物文件路径是否按 checkpoint/round 区分或原子提交；同名文件被覆盖时审计链是否仍完整 |
| "review_context 完整，reviewer 一眼看懂" | Reviewer 标准工作流读取的字段名/文件（如 `/tmp/code_changes.patch`）是否与 MACAO 实际发送的字段名/格式一致 |
| "checklist 全部 `[x]` / 已完成" | 是否有可核验的完成证据（PoC 结果、测试记录），而不是把"计划做"标记为"已做" |
| "AEP 定义 N 种消息类型" | 文档中出现"完整格式""详细格式"等措辞时，是否与实际给出详细 Schema 的消息类型数一致 |
| 同一实体的字段命名（如 checkpoint 标识） | 是否在 `.dev.yml` / `.review.yml` / `vote_result.json` / AEP payload / 摘要示例 中使用同一字段名；如故意分层命名，是否有文字说明原因 |

## 5. 术语、产物与已知简化边界

### 5.1 术语与产物一致性（唯一权威表）

必须维护一张"产物 — 生成者 — 路径 — 格式 — 关键字段 — 版本/保留策略"的唯一对照表（置于 PRD 附录），文档与代码中的所有示例字段必须能对照该表逐字段核验。禁止：

- 用不同名词描述同一决策结果（如 `REJECTED` vs `REWORK_REQUIRED` vs `REWORK`）；
- 把 MACAO 生成的 JSON 产物统称为"CLI 生成的 .yml 文件"；
- 摘要/改进说明文档中的示例字段名与权威基准文档中的 Schema 字段名不一致（如 `checkpoint` vs `checkpoint_ref` vs `checkpoint_id`）。

### 5.2 已知简化与决策项（缺陷与阶段性边界分离）

为了避免每轮重复争论既定的阶段性设计边界，必须维护一张常设的「已知简化」表（置于 PRD 附录或 `docs/reviews/STATUS.md`）：

| 项 | 现状 | 接受理由 | 接受轮次 | 生产化前需补什么 | 到期条件 (expiry) |
|---|---|---|---|---|---|

**执行规则**：
1. **已知简化不记为缺陷**：凡在表内列明且未到期的简化边界（例如单仓项目使用 In-repo 共享工作区、CI 门禁命令配置允许为 null 等），不作为代码缺陷处理，不占用 P0–P3 编号；
2. **决策项分类处理**：评审者若认为某项已接受的简化边界不再适用或存在业务风险，应单列为「**决策项**」，阐明具体的业务代价、安全隐患与修改建议，与纯代码缺陷严格隔离；
3. **严肃修订程序**：已知简化表的增删改查须按 §11 修订程序办理（触发问题 + 正反例 + 双人审阅），禁止单轮评审单方面认定或私自放宽；
4. **必须明确转正要求与有效期**：每一项必须写明「生产化前需补什么」，禁止仅记录模糊的「可接受」；每项须设定明确的 expiry（有效 commit 数或版本里程碑）；
5. **到期自动重新激活**：已知简化一旦到期或影响范围扩大，自动失去豁免效力，转为待处置条目重新进入门禁评审，严禁无感知默认续期。

## 6. 反例与边界场景库（MACAO 专用）

评审状态机、投票规则、Context 协议时，至少应对照以下场景逐一推演，并记录预期结果是否能从文档唯一推出：

```text
2-reviewer 全部弃权
2-reviewer 1 超时 + 1 批准
2-reviewer 1 批准 + 1 反对（1:1 僵局）
3-reviewer 1:1:1 三方不一致
Reviewer 进程崩溃后重启并重复提交投票
同一 checkpoint 收到两份同 reviewer_id 的 .review.yml（重试去重）
.dev.yml 缺少必需字段但 signal=EXPLICIT
第二轮返工时 .review.yml 是否覆盖第一轮记录
人工接管超时后系统的默认动作（是否静默按高置信度状态继续）
Git 冲突导致 checkpoint 引用的 commit 与工作区不一致
review_context 中的 diff/patch 字段与 Reviewer 工作流期望的载体（命令/文件/ref）不一致
```

每个场景应保存：来源文档/行号、预期结果、实际能否唯一推导、验证该场景所需的最小测试或推演步骤、**该场景失效时的影响**、以及**最后一次实际验证的 commit 与日期**。

沿用历史轮次的结论时，必须在「最后验证」列注明沿用来源，不得默认其在当前 commit 上仍然成立。

> **警示**：**成功样本只证明 happy path，不证明全量质量。** 局部的演示成功或单次端到端跑通，绝不能代替反例库中各异常分支的逐项击穿推演。

## 7. 失败路径、测试隔离与 L4 OPS 必测矩阵

### 7.1 失败路径与恢复测试隔离规则

1. 使用临时工作区（临时 git repo / `.macao/` 沙箱），不得污染真实项目仓库；
2. 不得使用真实 CLI 厂商账号额度进行破坏性测试；
3. 优先使用 fault-injection（模拟 PTY 断开、模拟消息丢失），避免真实 `kill -9` Adapter 进程作为唯一验证手段；
4. 测试结束需验证 `.macao/` 临时文件、锁与残留进程已清理；
5. 崩溃恢复类测试必须验证"重启后是否重复投票/重复生成产物"；
6. 演练与研究性脚本严禁向主仓库的生产状态数据库（`state.db`）或关键目录写入非审计脏数据。

### 7.2 L4 OPS 必测矩阵

申请 L4 / PG-3 门禁时，下表每一项都必须给出明确结论（`VERIFIED` / `PARTIALLY_VERIFIED` / `CONTRADICTED` / `NOT_APPLICABLE`），标注 `NOT_APPLICABLE` 必须写明充分的技术理由。缺漏任何一行即视为 L4 运维就绪度证据不完整：

| # | 运维与异常场景 | 预期行为与防护要求 |
|---|---|---|
| 1 | 守护进程在存在活跃任务时单次扫描 | 扫描不崩溃；对超时审查员生成 `REVIEWER_TIMEOUT_ABSTAIN` 记录；状态机安全进入 HOLD，绝不静默放行推进 |
| 2 | 守护进程常驻循环中遭遇内部异常 | 异常必须捕获并完整记录至审计事件与 stderr；严禁使用裸 `except: pass` 吞掉异常致使守护进程陷入假死或盲目空转 |
| 3 | Reviewer PTY 终端会话中途断开 | 该审查员计入超时/失败处置，其余审查员独立会话不受影响；确保清理子进程，无僵尸进程残留 |
| 4 | 独立 Worktree 沙箱创建失败 | 遵循 Fail-Closed 原则：严禁静默回退污染主工作区，立即阻断并清理部分创建的残留目录 |
| 5 | 系统崩溃后冷重启 | 幂等状态恢复：不重复投票、不重复生成覆盖产物；已被消费的任务产物绝不被二次消费 |
| 6 | 多进程/线程并发写 `state.db` | 具备明确的单写者协调或 SQLite WAL 锁超时重试机制；杜绝产生数据库锁死或半写入损坏状态 |
| 7 | 磁盘写入失败 / 存储空间不足 | 写入失败安全中断并报告，不得留下截断的半完成产物或伪造的状态转换事件 |
| 8 | 演练与测试结束后的现场清理 | `.macao/` 临时文件、文件锁、临时 worktree 挂载点与后台派发进程全部干净退出并注销 |
| 9 | **人工接管路径实机演练** | 具备真实人类交互输入的 `macao override resolve` 全程留痕；在操作员人工介入之前，系统保持安全 HOLD 状态 |
| 10 | **端到端演练的真实性与组件保真** | 端到端演练必须穿透真实生产组件（遵循 §9 模式 E），严禁由 runner 或 mock 脚本内部自行伪造 `YES_APPROVE` 审查意见或合成审计事件 |

*注：第 9 行是 §2.1 L4「人工接管路径实机演练」与 §3.3「用户可见的人工接管演练」的强制落地形式；第 10 行直接受 §9 模式 E 约束。*

## 8. 严重级定义、可达性定级与处置纪律

### 8.1 严重级的域定义（影响维度）

为了避免定级之争消耗轮次，MACAO 确立基于系统影响的判定标准：

| 级别 | MACAO 域定义 | 典型案例 |
|---|---|---|
| **P0** | 未经有效评审的代码可被合并；审计链在哈希/提交层面断裂；系统主流程崩溃无法启动 | 绕过投票直接触发 git merge；审计日志丢失或散列断链；主入口导入错误退出 |
| **P1** | 状态机违约（出现转移表外的路径 / 应阻断而放行）；票面完整性破坏（投票被伪造、丢失、反转或强行兜底）；历史产物被静默覆盖导致审计证据不可追溯 | 提取器将任意 YAML 伪造为 `YES_APPROVE`；返工轮次覆盖第一轮评审意见；非法状态强行迁移 |
| **P2** | 并发竞态条件；边界值处理不严密；进程与文件卫生不良；仅在特定低频异常场景下触发且有防御保护 | 提取器 ANSI 过滤幂等断言自指；未显式捕获次级超时异常；非核心元数据缺失 |
| **P3** | 代码可读性、格式排版、提示文档措辞、不影响业务逻辑判断的展示缺陷 | 终端输出拼写错误；注释失效；CLI 帮助文本不清晰 |

### 8.2 可达性维度（与影响维度联合定级）

确定系统影响类别后，必须结合该缺陷在当前代码路径中的**实际可达性**综合定级，杜绝脱离实际危害的过度定级或低估隐患：

1. **在线真实可达**：生产入口（CLI、Daemon、API）存在可直接触发该路径的正常或异常输入 → **维持影响类别对应的基础级别**；
2. **仅测试可达 / 生产无调用方**：核心逻辑存在缺陷但生产代码未接入（零调用方，见 §9 模式 E） → **下调一级**，并在条目中显式注明「接线即回升至 Px」，防止抢占真正紧急缺陷的修复资源；
3. **被上游严格校验阻断的防御性分支**：缺陷存在于下游代码，但已被上游 Schema 校验或前置卫语句完全阻断 → **下调一级**，必须在条目中精准指出阻断方的确切位置（`file:line`），并注明「上游校验一旦放宽即回升至 Px」。

*降级必须给出确切的技术理由与回升条件，严禁无理由定级。评审争议时应依据可达性证据下调并注明回升触发条件，不得单纯为了强调重要性而主观升级。*

### 8.3 处置规则与修复验证纪律

1. **P0/P1 强阻断性**：PG-1、PG-2、PG-3 门禁绝对不可豁免；必须完整记录 `issue_id`、`evidence`、`owner`、`due_date`、`resolution_commit`、`status`；
2. **P2/P3 风险接受完整规范**：可在明确风险接受后延期，但延期不等于"没问题"。「作者声明采纳 + reviewer 口头备注」不构成合规的风险接受。风险接受必须在 `docs/reviews/STATUS.md` 中完整登记以下字段：
   ```text
   issue_id:               缺陷标识（如 P2-CARRY-1）
   severity:               严重级（P2 / P3）
   first_commit:           首次提出的 commit SHA
   last_verified_commit:   最近一次实机复核的 commit SHA
   evidence:               确切证据定位（file:line 或归档脚本相对路径）
   owner:                  缺陷归属责任人
   risk_acceptor:          风险承担决策者（不可留空）
   scope:                  该项风险接受生效的边界与模块范围
   expiry:                 到期条件（具体 commit 数量、里程碑版本或到期日期）
   resolution_commit:      预期或最终修复 commit（未修复前填 null）
   status:                 RISK_ACCEPTED
   ```
   **到期自动重新阻断**：到期或该缺陷的影响范围扩大时，该条目**自动重新变为阻断项**，必须重新走正式审批流程，严禁无感默认续期。未完整履行登记的 P2/P3 视为未被接受，下一轮仍须阻断处置；
3. **验证修复，而非重报旧缺陷**：对上一轮已标注「已修复」的条目，评审者的核心职责是**构造严苛的反例去击穿该修复**，而非机械性地把原缺陷报告重复抄写一遍。凡声称「已修复」的 PR，必须附带针对性的自动化回归测试；
4. **测试不得以显式传参绕开生产路径**：回归测试若仅通过直接向内部函数注入预构造的中间状态（如显式传入模拟的超时名单、手动篡改私有标志位）来命中被测分支，仅能证明该分支语法可达，不能证明生产真实入口能够正确驱动该路径。验证修复时，必须至少包含一条由**真实生产入口**驱动的测试路径；
5. **真理不等于投票**：每项 REJECT / P0 / P1 必须附带可复现证据（确切文件路径 + 行号 + 逻辑反例），不以 reviewer 人数多寡或权威身份代替证据事实；
6. **沉默 ≠ 同意**：未表态或超时的 reviewer 严格不计入"赞成票"或"多数派"；
7. **结构性审计变更共识制**：产物落盘路径、核心状态枚举、投票仲裁公式等审计强相关变更，必须取得多 reviewer 一致共识，不适用简单多数票决。

## 9. 文档评审专用自审 Checklist（改编自原 §18 A–D 模式）

同一 reviewer 连续几轮对**同一类盲点**漏审时，必须显式登记（登记到当次 review 文件 §0）并激活对应 checklist 项。以下是文档对齐评审场景下已反复出现的通用盲点：

| # | 漏审模式 | 典型后果 |
|---|---|---|
| **A** | 字段声明位置 vs 代码/伪代码实际读取位置不一致（如字段声明在嵌套结构下，伪代码却从根路径读取） | 实现按伪代码编写后，字段永远读不到，运行时静默失败 |
| **B** | checklist `[x]` ≠ 已有完成证据 | 把"计划要做"误当作"已完成"合入决策 |
| **C** | 确定性语言（100%/99%/"无条件可信"）未标注"设计目标"还是"已验证事实" | 读者/实现者把设计目标当作已验证行为直接生产使用 |
| **D** | 代码块格式不可执行（JSON 内嵌 `#` 注释、字段名与正式 Schema 不一致的"示意"代码） | 实现者按示例直接照抄，产生无法解析的产物 |
| **E** | 「已实现」被当作「已接线」——新增模块的核心函数在生产代码中零调用方，或类字段声明后从不读取 | 交付物看似完整、单测全绿，实际核心链路从未运行过；端到端演练退化为自证循环，门禁证据失效 |

强制自检（文档评审每轮必查）：

```text
□ 1. 字段名 vs 实际读取路径是否一致？（正文 Schema vs 伪代码/示例）
□ 2. 每一处 [x] / "已完成" / "✅" 是否有对应证据，而非计划？
□ 3. 每一处 "100%" "99%+" "无条件" 等确定性用语是否标注了目标/待验证？
□ 4. 每一段声称是 YAML/JSON 的代码块是否真的能被解析（无非法注释、字段名与 Schema 一致）？
□ 5. 每个 REJECT/P0/P1 是否给出了可复现的文件路径 + 行号证据？
□ 6. 本轮新增/修改的每个核心函数、类字段，在 src/ 中是否有真实的生产调用方？
     - 检查方式：grep -rn "<符号名>" src/ ，排除定义处自身
     - 零生产调用方 = CLAIM_ONLY，不得作为任何门禁级别的放行证据，无论单测是否通过
     - 单测调用仅证明其语法可调用，不证明其已接入端到端实际业务流程
□ 7. 我复跑的每条命令，其参照系与作用域是否与结论完全一致？（见 §3.4 作用域对照表）
     - 是否盲目沿用了申请文档给出的命令而未质疑其参照系（如工作树 vs 提交、特殊环境 vs 干净环境）？
     - 负向测试是否断言了非零退出码与明确的错误日志？
```

## 10. 单次评审交付物模板

`docs/reviews/<yyyy-MM-dd>-review-result-<mid>-<reviewer>.md` 至少包含：

```markdown
# <评审对象> 对齐/评审结论

- 评审日期 / 评审范围 / 对齐或评审基准
- 结论（L1–L4，或 PG-0–PG-3 判定）
## 已对齐 / 已确认项
## P0：必须先解决
## P1：发布/进入下一阶段前应修正
## P2/P3：可延期但需登记
## 交叉文档需做的文字修订
## 建议的闭环顺序与验收标准
## 复现脚本与命令（含最后执行日期与完整可重放环境）
## Reviewer 自审记录（如有连续漏审，登记于此）
```

agmsg / 简报中只发送结论、1–2 个 blocker 与详细报告路径；完整证据保留在报告文件中。

## 11. 生效与修订

本方法论的修改必须：

1. 指明触发问题（例如某类漏审导致了什么后果）；
2. 提供至少一个正例和一个反例；
3. 不得把当前项目的临时状态（某次评审结论、当前 P0 列表）写入本文件正文，应写入 `docs/reviews/`；
4. 检查代码块可执行性与 Markdown 完整性；
5. 由至少两名 reviewer（或两次独立评审）审阅后生效。
