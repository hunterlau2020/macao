## 一、P1 核心阻断项逐项处置与闭环明细

### P1-1: `--dry-run` 无条件写盘，与「100% 零修改 / Pure Read-Only」矛盾
- **评审来源**: Muse B-1, Codex P1-05, Grok P1-1, Claude P1-1
- **根因分析**: `TeamProber.probe()` 在完成探活字典装配后，于末尾无条件调用 `self._write_probe_log(probe_result)`，导致即使指定 `--dry-run` 也会在本地创建 `.macao/logs/probe/` 目录并落盘 `probe_<timestamp>.log`。
- **闭环方案**:
  1. 在 `TeamProber._write_probe_log()` 函数入口处增加守卫：`if self.dry_run: return None`；
  2. 在 `probe()` 调用点处增加前置判断：`if not self.dry_run: log_file = self._write_probe_log(probe_result)`；
  3. 确保探活阶段对 SQLite（`mode=ro`）和文件系统均 100% 零修改、零写盘、零 DDL。
- **代码变更**: [`src/macao/workflow/prober.py`](file:///home/debian/macao/src/macao/workflow/prober.py)
- **验证测试**: [`tests/test_p1_closures_and_regressions.py:test_p1_1_prober_dry_run_zero_disk_mutation`](file:///home/debian/macao/tests/test_p1_closures_and_regressions.py) 断言在 dry-run 探测后，`.macao/logs/probe` 目录不存在，且本地零文件修改。

### P1-3: 进度三元组算法存在脏树遮蔽、单票过早终止与缺席名单缺失
- **评审来源**: Codex P1-03, Grok P2-2, Claude P1-3
- **根因分析**:
  1. `_derive_progress_triplet` 优先判定 `not git_info["is_clean"]`，导致未暂存脏改动遮蔽了客观存在的 `REVIEW_PENDING` 申请；
  2. `_inspect_physical_reviews` 以 `len(matching) == 0` 判定 pending，只要有 1 个 reviewer 提交结果即误判为不再 pending；
  3. `next_planned` 未列出期待但未出票的 reviewer 名单。
- **闭环方案**:
  1. 调整优先级：客观物理提审单（`has_pending_request`）优先级高于开发态脏树；若有脏改动，在三元组中作为附注说明，但宏观状态仍如实推导为 `REVIEW_PENDING`；
  2. 传入配置的评审员集合 `reviewers_cfg`，提取结果文件名中的评审员身份构建 `submitted_reviewers`，按集合差精确计算 `missing_reviewers`；只要 `len(missing_reviewers) > 0`，即判定 `has_pending_request = True`；
  3. `next_planned` 精确生成待落票名单：`Await pending reviews from: {', '.join(missing_reviewers)}`。
- **代码变更**: [`src/macao/workflow/prober.py`](file:///home/debian/macao/src/macao/workflow/prober.py)
- **验证测试**: [`tests/test_p1_closures_and_regressions.py:test_p1_3_progress_triplet_review_pending_with_partial_votes`](file:///home/debian/macao/tests/test_p1_closures_and_regressions.py) 测试 1/3 评审员落票 + 脏树，断言状态维持 `REVIEW_PENDING` 且 Next 正确列出未出票的 2 位评审员。

### P1-6: `macao clean` 默认删除全部运行时状态，`--restore` 无快照备份
- **评审来源**: Claude P1-6
- **根因分析**: 默认 `macao clean` 直接 `shutil.rmtree(".macao")` 删除了所有运行时（含 `state.db` 和日志），未兑现 PRD 承诺的仅清理临时 worktree；`--all` 从未创建 `.macao.bak.<ts>` 目录快照；`--restore` 在恢复前执行了破坏性删除。
- **闭环方案**:
  1. **默认 `macao clean`**: 仅安全清理 `.macao/worktrees/` 下已完成或废弃的临时工作树沙箱，严禁触碰 `.macao/state.db`、日志或配置文件；
  2. **`--all`**: 执行任何破坏性删除前，强制通过 `shutil.copytree` 创建目录级完整快照 `.macao.bak.<timestamp>/`，并对 `macao.yaml` 进行同时间戳备份，再清空运行时；
  3. **`--restore`**: 绝不预先清空运行时，而是搜索最新 `.macao.bak.*` 目录和 `macao.yaml.bak.*` 文件进行无损还原。
- **代码变更**: [`src/macao/cli/main.py`](file:///home/debian/macao/src/macao/cli/main.py), [`tests/test_clean_and_rollback.py`](file:///home/debian/macao/tests/test_clean_and_rollback.py)
- **验证测试**: [`tests/test_p1_closures_and_regressions.py:test_p1_6_clean_snapshot_and_safe_defaults`](file:///home/debian/macao/tests/test_p1_closures_and_regressions.py) 完整断言默认清理的非破坏性、`--all` 的快照生成、以及 `--restore` 的数据级恢复。

### P1-7: `task checkpoint --auto` 无条件写入 `tests_passed: true`
- **评审来源**: Codex P1-01, Claude P1-7
- **根因分析**: CLI 在生成 `.macao/.dev.yml` 时硬编码写入 `tests_passed: true`，在执行者未运行或未通过测试的情况下直接欺骗状态机推进到 `READY_FOR_REVIEW`。
- **闭环方案**:
  1. 移除硬编码：`--auto` 默认将 `tests_passed` 设为 `False`；
  2. 引入真实门禁：新增 `--test-cmd <cmd>` 选项，由子进程实际运行该命令，仅当 exit code == 0 时才允许记录 `tests_passed: True`；
  3. 引入显式免测：支持 `--tests-exempt` 显式标记免测；
  4. 若既未提供测试命令通过凭据也未免测，`tests_passed` 为假，`orchestrator.check_development_checkpoint()` 严格阻断推进。
- **代码变更**: [`src/macao/cli/main.py`](file:///home/debian/macao/src/macao/cli/main.py)
- **验证测试**: [`tests/test_p1_closures_and_regressions.py:test_p1_7_checkpoint_auto_does_not_fabricate_tests_passed`](file:///home/debian/macao/tests/test_p1_closures_and_regressions.py) 断言 `--auto --no-review` 未经测试认证时保持 `tests_passed: false` 并阻断 FSM 推进。

### P1-8: `macao task create --force` 绕过唯一活动任务约束并丢失用户验收标准
- **评审来源**: Codex P1-02, Claude P1-8
- **根因分析**:
  1. `--force` 存在时直接跳过检查创建新任务，导致旧任务孤立在非终态（成为僵尸任务）；
  2. CLI 将 `--acceptance` 包装为 dict，导致编排器内部 `isinstance(acceptance_criteria, list)` 判定失败，退化为默认列表，用户传入的标准丢失。
- **闭环方案**:
  1. **活动任务不变量与显式生命周期闭环**: 当存在活动任务且用户显式指定 `--force` 时，强制调用 `orchestrator.cancel_task(old_task_id, reason="Superseded by forced new task creation")`，使前序任务合法触发 `E10` 转移至 `CANCELLED` 终态并记录审计事件，杜绝孤立僵尸任务；
  2. **验收标准逐字段原样透传**: CLI 解析 `--acceptance` 为字符串列表，编排器增强支持 `list`/`str`/`dict` 多态解析，确保用户显式传入的标准逐字段出现在发给执行者的 `DEVELOPMENT_STARTED` Type A 信封中。
- **代码变更**: [`src/macao/cli/main.py`](file:///home/debian/macao/src/macao/cli/main.py), [`src/macao/workflow/orchestrator.py`](file:///home/debian/macao/src/macao/workflow/orchestrator.py)
- **验证测试**: [`tests/test_p1_closures_and_regressions.py:test_p1_8_task_create_force_cancels_old_task_and_preserves_acceptance`](file:///home/debian/macao/tests/test_p1_closures_and_regressions.py) 断言旧任务被 E10 取消归档且新任务成为唯一活动任务。
