## 修订 1　§9 新增漏审模式 E：「已实现」≠「已接线」

### 触发问题

`3c5ed32` 轮申请 L4/PG-3，六项交付物中三项的核心函数**从未被生产代码调用过一次**，而全量 72 项测试 100% 通过。评审若只看「测试全绿 + 代码存在」，会把三个从未运行过的模块判为已交付。

### 后果

L4 的端到端证据（`macao live-run`）实际不经过任何 Phase 3 组件：派发器被实例化后从不读取，解析器被导入后从不使用，三份「审查意见」由 runner 自己写死为 `YES_APPROVE`，「人工签字」是自动生成的审计事件。整条演练是自证循环。

### 反例（本轮实证）

```bash
$ grep -rn "dispatch_review_in_worktree" src/ tests/
src/macao/workflow/live_dispatcher.py:117:    def dispatch_review_in_worktree(   # 唯一出现，即定义处本身
```

Phase 3 的头号交付物，全仓**零调用方、零测试**。同族证据：

- `src/macao/workflow/live_runner.py:36` 声明 `self.dispatcher`，`:73` 赋值，此后全文无一次读取；
- `src/macao/workflow/live_runner.py:15` 导入 `ReviewExtractor`，pyflakes 报 `imported but unused`；
- `src/macao/workflow/live_dispatcher.py:109` 声明 `self.active_sessions`，全类无一次读取；
- `src/macao/workflow/daemon.py:39-66` 的超时降级分支，因 `:34` 调用了不存在的方法而从未执行过一次。

一条 `grep` 即可定位全部四处，耗时不足五分钟。

### 正例（本项目既有实践）

`8296f3c` 轮授予 L3/PG-2 时，我对 E6 返工门禁做的是**四分支实机驱动**（identical / new / revert-to-consumed / third-new commit），每一分支都经由生产入口 `check_development_checkpoint` 触发并观察状态迁移——即证明了代码存在，也证明了它在生产路径上被调用且行为正确。这是「已接线」的证据标准。

### 建议条文

在 §9 的漏审模式表末尾新增一行：

```markdown
| **E** | 「已实现」被当作「已接线」——新增模块的核心函数在生产代码中无调用方，或对象字段声明后从不读取 | 交付物看似完整、单测全绿，实际从未运行过；端到端演练退化为自证循环，门禁证据失效 |
```

并在 §9 的强制自检代码块中新增第 6 项：

```text
□ 6. 本轮新增/修改的每个核心函数、类字段，在 src/ 中是否有生产调用方？
     - 检查方式：grep -rn "<符号名>" src/ ，排除定义处自身
     - 零调用方 = CLAIM_ONLY，不得作为任何门禁级别的证据，无论其单测是否通过
     - 单测调用不算生产调用方；tests/ 中的调用只证明可调用，不证明在流程中
     - 反例：交付物声明「已实现真实派发」，而派发函数全仓仅在定义处出现一次
```

## 修订 2　新增 §3.4「验证命令的作用域」

### 触发问题

同一族问题在最近三轮各出现一次，被三位不同评审者当作三个孤立缺陷分别处理：**绿灯是在与结论不同的参照系里测出来的**。

| 轮次 | 参照系 | 声明 | 实际 |
|---|---|---|---|
| `4e38ed6` | **平台** | 单测全绿 | 断言硬编码 POSIX 分隔符，win32 下 64/65（ZCode P1-1，已修） |
| `3c5ed32` | **环境** | `Ran 72 tests, OK (100% PASS)` | 依赖 PATH 上恰好装有 AI CLI；干净 PATH 下 FAILED（P2-NEW-8） |
| `3c5ed32` | **版本** | `git diff --check` → `Exit Code 0, 100% Clean` | 该命令检工作树，提交后恒 rc=0；`git show --check` 为 rc=2（P3-NEW-17） |

### 后果

结论的适用范围被静默放大。三次分别修补三个症状，不能阻止第四次以新的参照系出现。**本提案人自己是第三次的受害者**：我在 `3c5ed32` 轮初稿中沿用了申请文档给出的 `git diff --check` 并判为 VERIFIED，未质疑其作用域，经 glm 的对比报告提示后才改判——这说明它不是作者单方面的疏忽，而是评审侧同样缺少的一条检查。

### 反例（本轮实证）

```bash
$ git diff --check ; echo rc=$?            # 工作树参照系
rc=0                                        # 提交后恒为空，零信息量

$ git show --check 3c5ed32 ; echo rc=$?     # commit 参照系（正确）
docs/reference/REVIEW_METHODOLOGY.md:4: trailing whitespace.
docs/reference/REVIEW_METHODOLOGY.md:5: trailing whitespace.
docs/reference/REVIEW_METHODOLOGY.md:6: trailing whitespace.
rc=2
```

```bash
$ PATH=/usr/bin:/bin PYTHONPATH=src python3 -m unittest \
    tests.test_phase3.TestPhase3Engine.test_wizard_probes_and_smart_config
AssertionError: False is not true          # tests/test_phase3.py:67
FAILED (failures=1)
```

### 正例

同一轮的 Schema 打包验证：结论是「`pip install` 后路径不再脱钩」，参照系就是「一个干净的、装了本包的 venv」，因此验证在 `python3 -m venv` + `pip install` 的产物中执行，而非在源码树中 `PYTHONPATH=src` 执行。参照系与结论一致，结论成立。

### 建议条文

在 §3.3 之后新增：

```markdown
### 3.4 验证命令的作用域

每条 TEST/OPS 证据必须声明其**参照系**，且参照系须与结论的适用范围一致。结论说的是哪个对象，
命令就必须作用在哪个对象上。

| 结论谈的是 | 必须的参照系 | 常见的错误参照系 |
|---|---|---|
| 某个 commit 是否洁净 | `git show --check <full_sha>` | `git diff --check`（检工作树，提交后恒 rc=0） |
| 某个 commit 的测试是否全绿 | 该 commit 的干净 checkout / worktree | 含未提交改动的工作树 |
| 在任意环境可用 | 受控的最小 PATH / 容器 | reviewer 自己装满工具的开发机 |
| 跨平台可用 | 各目标平台各跑一次；无条件时明确降为 CODE 推理 | 单一平台实跑后外推 |
| 安装后可用 | 干净 venv 的 `pip install` 产物 | 源码树 + `PYTHONPATH=src` |

作者与 reviewer 双方都须自检。凡参照系与结论不一致的绿灯，验证状态最高只能记为
`PARTIALLY_VERIFIED`，并注明其成立条件；作者在申请文档中给出的命令不构成 reviewer
免于自检的理由。
```

同时在 §9 的强制自检代码块中新增第 7 项：

```text
□ 7. 我复跑的每条命令，其作用域是否与我要下的结论一致？（见 §3.4 对照表）
     - 尤其：我是否沿用了申请文档给出的命令而未质疑其参照系？
```

## 修订 3　新增 §3.5「复现证据的归档」

### 触发问题

指引 §3.3 要求 L3 的 SIM/TEST 证据为 VERIFIED，§8 要求「每项 REJECT/P0/P1 必须附可复现证据」。但**从未规定复现脚本存放何处**，因此历轮的反例脚本一律写在 `/tmp` 或会话临时目录，会话结束即消失。

### 后果

SIM 证据在下一位评审者手中**不可证伪**。复审者只能选择相信报告里贴出的输出，或从零重建实验——这恰好是指引 §8「真理不等于投票」要防的东西：当证据不可重放时，结论的成立与否重新退化为「谁说的」。

### 反例（本轮实证）

`3c5ed32` 轮三条 P1 全部依赖复现脚本：

- `repro_extractor.py`（5 例，证明任意 YAML 被伪造成 `YES_APPROVE`）
- `repro_daemon2.py`（3 段，证明 `scan_once` 必崩且 `run_loop` 静默吞掉）
- `repro_archive.py`（证明归档链未断、断的是 UI 渲染）

三者均位于会话 scratchpad，本报告提交后即不可访问。报告中只留下了它们的**输出**——而输出正是「作者自述、成功日志」一类被指引明确排除的证据形态。

### 正例

Washdb §3.2 的证据记录格式要求每条证据保存 `query_or_test`（可复现命令）与 `result_artifact`（相对路径），§11 进一步要求输出持久化、结论钉死不可变输入。本项目已自发做到「钉死完整 commit SHA」（`P3-NEW-10` 的教训），缺的是脚本本体的归档。

### 建议条文

在 §3.4 之后新增：

```markdown
### 3.5 复现证据的归档

任何用于支撑 P0/P1 结论或 SIM/TEST 状态的脚本，必须随报告归档，不得只存在于终端滚屏或临时目录。

- 归档位置：`docs/reviews/evidence/<yyyy-MM-dd>-<short_commit>-<reviewer>/`；
- 单文件脚本可改为内联在报告的「附：复现脚本」章节中，但必须是**完整可粘贴执行**的，
  不得省略为片段；
- 每个脚本须在报告中登记：所验证的 issue_id、执行时的完整 commit SHA、依赖的外部前提
  （网络、已安装的 CLI、平台），以及**最后一次实际执行的日期**；
- 脚本若依赖临时目录，须由脚本自身创建（`tempfile.mkdtemp`），不得依赖 reviewer 手工准备的状态。

「报告里贴了输出」不等于证据可复现。复审者应当能够只凭归档物重放该发现。
```

并在 §10 的交付物模板中，于 `## Reviewer 自审记录` 之前插入一行：

```markdown
## 复现脚本与命令（含最后执行日期）
```

## 修订 4　§8 新增「修复验证纪律」

### 触发问题

本项目面板约用七轮才自发收敛出「验证修复，而不是重复发现旧缺陷」的打法，且从未成文；新加入的 reviewer 无从继承。Backend 指南 §0.4 已有现成条文。

### 后果

两种相反的浪费同时存在：一是把已修复的旧缺陷重新报一遍，占用篇幅与仲裁资源；二是**接受了修复声明却没有击穿它**——后者代价更大。

### 反例（本项目史实）

`7973853` 轮：仓库的 64/64 全绿，而其中一条测试的 docstring 写着「fails closed on **missing** EXPLICIT signal」，三个用例却全都携带 `signal: EXPLICIT`——测试名断言的性质，其用例从未实际触及（即指引 §9 pattern B）。修复声明只有在**构造反例去击穿它**时才被证伪。

同族反例：`3e1a991` 轮我发现仓库测试以显式传参 `timed_out_reviewers=[...]` 驱动超时逻辑，绕过了生产路径上的 `detect_timed_out_reviewers()`；改用 `timeouts: {"per_reviewer": "2s"} + time.sleep(2.5)` 驱动真实生产路径后，缺陷立即暴露。

### 正例

`8296f3c` 轮对 P1-NEW-12 的验证：不是复述作者的修复说明，而是自建 3 个真实 commit 跑四分支矩阵（identical / new / revert-to-consumed / third-new），四条路径的实际状态迁移全部符合预期，才判定该修复成立。

### 建议条文

在 §8 的要点列表末尾新增：

```markdown
- **验证修复，而非重报旧缺陷**：对标注「已修复」的条目，评审动作是**构造反例去击穿修复**，
  不是把原缺陷再报一遍。修复声明必须附回归测试才算数；
- **测试不得以显式传参绕开生产路径**：回归测试若通过直接注入中间状态（如显式传入超时名单、
  预置内部标志）来触发被测分支，只证明了分支可达，不证明生产入口会到达它。
  验证修复时必须至少有一条路径从**生产入口**驱动；
- **成功样本只证明 happy path**：一次全绿的端到端演练不构成全量质量证据（见 §6）。
```

## 修订 5　§8 新增影响导向定级表与可达性维度

### 触发问题

指引现无严重级的域定义，仅有「P0/P1 不可豁免」的处置规则。后果是定级之争反复消耗轮次：`7973853` 与 `3ea5256` 两轮中，同一缺陷 claude 判 P1、qwen 判 P2，双方各自论证影响，无共同判据。

### 我与 glm 提案的分歧

glm 建议的影响导向表（P0 = 未评审代码被合并 / 审计链断裂；P1 = 状态机违约 / 票面完整性破坏）方向正确，但**只按影响类别定级会产生新的争议**。本轮即撞上：`P1-NEW-13`（`ReviewExtractor` 把任意 YAML 伪造成 `YES_APPROVE`）**正是**「票面完整性破坏」，但其所在函数全仓零调用方，当前危害是潜在而非现实的。若只看影响类别，它与一个正在线上伪造投票的缺陷同级——这既不公允，也会让作者对真正紧急的缺陷失去优先级判断。

因此我建议在影响维度之外补一个**可达性维度**。这正是我本轮给 `P1-NEW-13` 定 P1 而非 P0、给 `P2-NEW-7` 定 P2 而非 P1 的实际依据；目前它只是我的私人判断，应当成为规则。

### 反例与正例（同一轮的两个相反判断）

- **反例（若无可达性维度）**：`P1-NEW-13` 影响类别为「票面完整性破坏」→ 按纯影响表应为 P0，但该函数零调用方，判 P0 会误导作者的修复排序。
- **正例（有可达性维度）**：`P2-NEW-7`（`vote.py:97` / `orchestrator.py:557` 重新引入 `YES_APPROVE` 兜底）影响类别同为票面完整性，但 `vote.py:39-41` 在收集阶段已做 Schema 校验、schema `required` 含 `vote`，故 `or` 右支当前**不可达**——降为 P2 并注明「校验一旦放宽即回升」。两条同影响类别、不同可达性的缺陷，据此得到不同且可复核的定级。

### 建议条文

在 §8 开头新增：

```markdown
### 8.1 严重级的域定义（影响维度）

| 级别 | MACAO 域定义 |
|---|---|
| **P0** | 未经有效评审的代码可被合并；审计链在哈希层面断裂；系统无法启动 |
| **P1** | 状态机违约（出现转移表外的路径 / 应阻断而放行）；票面完整性破坏（投票被伪造、丢失或反转）；产物覆盖导致证据不可追溯 |
| **P2** | 并发竞态；边界正确性；健壮性与过程卫生；仅在特定条件下触发 |
| **P3** | 可读性、冗余、文档措辞、不影响判断的展示缺陷 |

### 8.2 可达性维度（与影响维度联合定级）

确定影响类别后，按缺陷路径当前是否可达调整一级：

- **在线可达**：生产入口存在可触发该路径的输入 → 保持影响类别对应的级别；
- **仅测试可达 / 无生产调用方**：**降一级**，并在条目中显式注明「接线即回升至 Px」；

  同时必须指出是哪一处上游校验在挡（给出 `file:line`）。

降级必须写明理由与回升条件，不得只写级别。拿不准时降一级并注明理由，不得为强调重要性而升级。
```

## 修订 6　§8 风险接受登记补全与到期自动重新阻断

### 触发问题

指引现要求 P0/P1 记录 `issue_id / evidence / owner / due_date / resolution_commit / status`，但 P2/P3 的「明确风险接受」无字段要求，也无到期机制。

### 后果

P2 无限期携带，每轮被重新提起、重新论证、重新搁置。

### 反例（本项目史实，可数）

`P2-CARRY-1`（`src/macao/adapter/integ_harness.py:115` 的 ANSI 断言自指——`clean_logs` 已在 `pty_session.py:89`/`:96` 用同一条正则 strip 过，该断言等价于「strip_ansi 幂等」，无法证伪「ANSI 过滤有效」）：底层问题最早记录于 `4df059e` 轮（当时表述为「`ansi_stripped_ok` 仍为无条件常量」），以 `P2-CARRY-1` 编号首次出现于 `bf5ae2d` 轮，至本轮 `3c5ed32` 仍未修，**横跨 11 个待审 commit**（`4df059e`、`7935da3`、`bf5ae2d`、`e7ba2d2`、`ea536ab`、`f41b9da`、`3e1a991`、`7973853`、`3ea5256`、`8296f3c`、`3c5ed32`）。它从未被正式风险接受，也从未到期——只是每轮被重新抄写一遍。

### 正例

Washdb §14.1 的登记字段含 `risk_acceptor / scope / expiry`，并明确「『采纳 + 备注』不构成风险接受。到期或扩大范围后自动重新阻断」。

### 建议条文

把 §8 中 P2/P3 一条改写为：

```markdown
- **P2/P3**：可在明确风险接受后延期，但延期不等于「没问题」。风险接受必须登记：

  ```text
  issue_id
  severity
  首次提出的 commit / 最近一次复核的 commit
  evidence（file:line 或归档脚本路径）
  owner
  risk_acceptor        # 谁承担这个风险，不得留空
  scope                # 该接受在什么范围内有效
  expiry               # 到期的 commit 数或日期
  resolution_commit
  status
  ```

  「作者采纳 + reviewer 备注」不构成风险接受。**到期、或缺陷影响范围扩大后，该条目自动
  重新阻断**，须重新走一次风险接受流程，不得默认续期。未完成登记的 P2/P3 视为未被接受，
  下一轮仍须处置。

  登记表维护于 `docs/reviews/STATUS.md`（实时状态，按 §1.3 不入本文件正文）。
```

## 修订 7　§7 新增 L4 OPS 必测矩阵

### 触发问题

`OPS` 在整份指引中只出现两次：§3.1:90 的类型定义、§3.3:108 的「L4：OPS 为 VERIFIED」。**没有任何一处说明 OPS 需要覆盖什么**。§7 有 5 条隔离规则，规定的是测试「怎么做」，不是「必须做哪些」。

### 反例（本轮实证）

申请文档的「后台守护扫描」一行写着 `Single scan completed, Exit Code 0 ✅ PASS`。实测 rc=0 属实，但走的是「无活跃任务时提前返回」的空转分支；一旦存在 `WAITING_REVIEW` 任务：

scan_once RAISED: AttributeError 'StateStore' object has no attribute 'get_audit_events'
run_loop(max_ticks=3) returned normally; no error surfaced to operator
REVIEWER_TIMEOUT_ABSTAIN count: 0

对应的单测名为 `test_daemon_scanner_single_tick_idle`——用例名自己就写明是 `idle`。

Washdb §10.2 的 11 行风险驱动测试矩阵（测试 → 预期），每行都是一个必须被回答的问题，且明确「P0/P1 相关测试全部通过后才可达到 L3；NOT_APPLICABLE 必须有理由」。

把现 §7 编为 §7.1，其后新增：

```markdown
### 7.2 L4 OPS 必测矩阵

申请 L4/PG-3 时，下表每一行都必须给出结论（VERIFIED / PARTIALLY_VERIFIED / CONTRADICTED /
NOT_APPLICABLE），`NOT_APPLICABLE` 必须写明理由。缺行即视为 L4 证据不完整。

| # | 场景 | 预期 |
|---|---|---|
| 1 | 守护进程在存在活跃任务时单次扫描 | 不崩溃；超时者生成 `REVIEWER_TIMEOUT_ABSTAIN`；进入 HOLD，不静默推进 |
| 2 | 守护进程长驻模式下遇到内部异常 | 异常落审计与 stderr；不得被裸 `except: pass` 吞掉 |
| 3 | Reviewer PTY 会话中途断开 | 该 reviewer 计入超时处置，其余不受影响；无僵尸进程 |
| 4 | Worktree 创建失败 | fail-closed：拒绝回退到主工作区；已创建的部分被清理 |

| 7 | 磁盘写入失败 / 空间不足 | 失败可恢复，不留下半完成的归档或半推进的状态 |
| 8 | 演练结束后的清理 | `.macao/` 临时文件、锁、worktree、子进程全部清理 |
| 9 | **人工接管路径实机演练** | 有真实人类输入的 `macao override resolve` 全程记录；系统在人类介入前保持 HOLD |
| 10 | 端到端演练的真实性 | 演练必须经过被认证的生产组件（见 §9 模式 E），不得由演练脚本自行伪造中间产物 |

第 9 行同时是 §2.1 L4「人工接管路径实机演练」与 §3.3「用户可见的人工接管演练」的落地形式；
第 10 行同时受 §9 模式 E 约束。
```

## 修订 8　§6 反例库补两列并恢复被删的一句话

### 触发问题

本指引 §6 由 Washdb §9 改编而来，改编时**丢失了两个字段和一句话**：

| | Washdb §9（源，`docs/reference/REVIEW_METHODOLOGY.md:400`） | MACAO §6（现，`docs/MACAO_REVIEW_GUIDELINES.md:158`） |
|---|---|---|
| 保存字段 | 来源 commit、预期、复现 SQL/测试、**影响**、**最后验证 build** | 来源文档/行号、预期结果、实际能否唯一推导、最小测试或推演步骤 |
| 收尾警示 | 「**成功样本只证明 happy path，不证明全量质量**」 | （无） |

### 后果

- 缺「最后验证」列，是携带项能无限漂移的机制性原因——没有任何人被要求声明某条目上次真正重跑是什么时候（见修订 6 的 `P2-CARRY-1`，11 个 commit 无人被要求填这一格）。
- 缺「影响」列，导致场景库无法用于排序，每轮从头判断哪个场景更要紧。
- 缺那句警示，与本轮的核心问题直接呼应：一次全绿的 happy-path 演练被当作全生命周期证据提交申请 L4。

### 正例

`8296f3c` 轮的六场景对账中，我对每个场景都记录了「本轮是否实际重跑」，因此能确认六场景在该 commit 上同时成立，而非沿用历史结论。这正是「最后验证」列要制度化的东西。

### 建议条文

把 §6 结尾一句改写为：

```markdown
每个场景应保存：来源文档/行号、预期结果、实际能否唯一推导、验证该场景所需的最小测试或推演步骤、
**该场景失效时的影响**、以及**最后一次实际验证的 commit 与日期**。

沿用历史轮次的结论时，必须在「最后验证」列注明沿用来源，不得默认其在当前 commit 上仍然成立。

**成功样本只证明 happy path，不证明全量质量。**
```

## 修订 9　§5 新增「已知简化表」（决策项与缺陷分离）

### 触发问题

指引 §8 处理的是「缺陷的等级与豁免」，但没有「这根本不是缺陷」这一类别。因此每轮都要重新争论某项到底是缺陷还是已被接受的阶段性边界。

### 后果

同一议题反复进入仲裁。glm 报告举的例子（kimi 的 ping 机制与实现不一致，本质是阶段性决策却每轮重辩）与本轮的 `ci_gate_command: null` 是同一类：后者在 `merge/controller.py:87` 明确写着 "Optional CI gate"，schema `macao_config.schema.json:63` 明确允许 `null`，属既定设计——我在本轮报告中把它单列为「决策项」而非缺陷，但这个做法目前没有任何条文支持，纯属个人判断。

### 正例

Backend 指南 §1.2 维护一张常设的「已知简化」表（项 / 现状 / 备注），并在 §0.3 规定：「§1.2 的已知简化是已接受的 MVP 边界，不记为缺陷；认为不可接受时单列为『决策项』，说明业务代价，不与缺陷混淆。」

### 反例

若无此表，本轮的 `ci_gate_command: null` 有两种同样「有理」的处理：判 P2（合并可无 CI 门禁）或不记（schema 明确允许）。两种处理都会在下一轮被另一位评审者推翻。

### 建议条文

把现 §5 编为 §5.1，其后新增：

```markdown
### 5.2 已知简化与决策项

维护一张常设的「已知简化」表（建议置于 PRD 附录，与 §5.1 的产物权威表并列）：

| 项 | 现状 | 接受理由 | 接受轮次 | 生产化前需补什么 | expiry |
|---|---|---|---|---|---|

规则：

1. 表内项目**不记为缺陷**。评审者若认为某项不可接受，应单列为「**决策项**」，写明业务代价与
   建议，不与缺陷条目混淆，也不占用 P0–P3 编号；
2. 表的增删改按 §11 的修订规则办理（触发问题 + 正反例 + 两名 reviewer），不得由单轮评审
   单方面认定；
3. 每项必须写明「生产化前需补什么」，不得只写「可接受」；
4. 每项有 expiry；到期未处置则自动转为待处置条目，重新进入评审范围（与 §8 的风险接受到期
   机制一致）。
```
