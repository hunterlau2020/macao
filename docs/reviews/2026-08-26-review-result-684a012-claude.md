## 一、产品设计完备性

### 已经做得扎实的部分（先给出正向评价，避免只列问题）

- 用户旅程覆盖了从 `preflight` → `init` → `doctor` → `task create` → `status` → `override resolve` → 归档的完整闭环（`MACAO_PRD_v2.md:1331-1339`），CLI 命令面与 `kubectl`/`terraform` 一类工具的心智模型接近，对目标用户（会用 CLI 的开发者）友好。
- §15.5 新增的"评审质量评测计划"（`MACAO_PRD_v2.md:1393-1400`）是本次修订中最有价值的补充：明确要构造 ≥20 个已知缺陷样本、测量共识召回率，并设定 **召回率 <60% 则重新评估角色分配** 的熔断线。这把"多 Reviewer 共识有没有用"从一句口号变成了可证伪的验收标准，是罕见的、值得保留的设计纪律。
- 安全边界一节（`MACAO_PRD_v2.md:1380-1387`）覆盖了 prompt injection、凭据泄露、代码外发到第三方厂商、ToS 合规四类风险并给出缓解措施，比多数早期 PRD 更进一步。

### 设计洞 1（P0）：合并后失败（CI Gate）没有对应的状态回退路径

**证据**：

- 统一转移表 `MACAO_PRD_v2.md:792`（E4）：`vote_result.json` 决策 = `APPROVED` → 目标状态 **`DONE`**，伴随动作包含"Merge Controller 执行合并策略；**发送 `MERGE_COMPLETED`**；本轮产物归档"——这三件事被列为 E4 触发时**同时**发生的动作。
- 但 §14.5 Merge Policy（`MACAO_PRD_v2.md:1362-1364`）描述的实际顺序是：`E4 触发后由 Merge Controller 执行：检出工作分支 → merge → （可选）CI gate 通过后才推送 → 合并完成才推送 MERGE_COMPLETED；CI 失败视为返工，生成新一轮 REWORK_REQUEST`。
- 两处对不上：如果 E4 触发即视为进入 `DONE`（转移表的字面意思），那么"CI 失败 → 生成新一轮 `REWORK_REQUEST`"要求系统从 `DONE` 回到 `REWORK`，但整张统一转移表（`MACAO_PRD_v2.md:785-796`）里**没有任何一条从 `DONE` 出发的边**；如果 CI Gate 其实是 E4 落地前必须先通过的子步骤，那么 `MERGE_COMPLETED` 就不应该是"E4 触发时"就发送的动作，转移表的措辞需要改成"CI Gate 通过后才进入 DONE"。

**影响**：这正是此前几轮评审反复揪出的同一类问题（状态机文字描述与实际时序不一致），只是这次出现在新增的 Merge Policy 与既有转移表之间。按当前文字，一个通过两个 AI Reviewer 投票但 CI 挂掉的变更，其系统状态无法从文档唯一确定。

**建议**：二选一并显式写清楚——(a) 把 CI Gate 挪到 E4 的前置条件里，`vote_result.json`=APPROVED 只是进入一个新的中间状态（如 `MERGING`），CI 通过后才转 `DONE` 并发 `MERGE_COMPLETED`；(b) 保持 E4→DONE 即时生效，但显式增加一条 `DONE → REWORK`（因 CI Gate 失败）的转移边并写明为什么这不违反"DONE 是终态"的直觉。

### 设计洞 2（P0）：Reviewer 的执行权限边界（sandbox / blast radius）未定义

**证据**：

- Adapter Contract（`MACAO_PRD_v2.md:1240-1250`）只定义了生命周期与消息接口（`start/stop/inject_task/ack/cancel` 等），没有任何字段约束 Reviewer Adapter 的**执行权限**——是否只读、能否联网、能否安装依赖、能否修改工作区文件。
- Capability Manifest（`MACAO_PRD_v2.md:1252-1261`）里有 `supports_worktree`（是否支持 git worktree 隔离评审），但 MVP 准入矩阵（`MACAO_PRD_v2.md:1263-1269`）完全没有列出这一列的取值——即 codex/kimi 是否真的会被隔离在独立 worktree 里评审，文档没有给出答案。
- §5.3 Reviewer 标准工作流（`MACAO_PRD_v2.md:988-1004`）里，Reviewer 除了 `git diff` 之外还会执行 `pylint src/`、`bandit -r src/`、`mypy src/`——这些都是对**本地工作区**的任意命令执行，而 Codex/Kimi 是通用 coding agent CLI（不是受限的静态分析工具），理论上具备编辑文件、执行任意 shell 命令、发起网络请求的能力。整个文档没有任何一处声明"Reviewer 在评审期间被限制为只读 / 沙箱执行"。

**影响**：这个产品的核心机制是"把本地真实代码仓库交给两个第三方厂商的通用编码 Agent 去跑，并让它们的输出决定是否自动合并到 `default_branch`"。风险表（`MACAO_PRD_v2.md:1160`）已经承认"Reviewer 被 prompt injection 操纵投票"的风险，但缓解措施只覆盖了"评审产物 Schema 校验"这一个环节，没有回答更根本的问题：**如果 Reviewer 本身在评审过程中被诱导执行了破坏性命令（而不只是给出错误的投票），谁来阻止它？** 这是一个比"投票被操纵"更严重的攻击面，当前设计完全没有约束。

**建议**：在 Adapter Contract 里加一个显式的执行权限声明（如 `execution_mode: read_only | sandboxed | full`），MVP 阶段 Reviewer 强制要求 `supports_worktree=true` 且在独立 worktree/容器中执行，不允许直接操作 Executor 的工作区；网络访问、包安装等高风险操作需要显式白名单。

### 设计洞 3（P1）：没有"强制人工确认后再合并"的策略开关

**证据**：`macao.yaml` 的 `policy` 段（`MACAO_PRD_v2.md:1300-1304`）只有 `consensus_rule` / `min_effective_votes` / `max_rework_rounds` / `review_strategy`，没有任何"是否要求人工在合并前签字"的开关；§14.5 描述的默认路径是两个 AI Reviewer 达成共识后 Merge Controller **直接**合并到 `default_branch`，人工只在 HUMAN_OVERRIDE（僵局/异常）时才会被拉入。

**影响**：产品定义里 MACAO 面向的是"AI 软件开发团队"，但正常路径下人类开发者对自己代码是否被合并**没有否决权**，只有在系统检测到分歧或异常时才会问人类。对真实代码库（尤其共享仓库、`default_branch` 常等价于生产线）而言，这是一个会显著影响采用意愿的设计缺口，而不是锦上添花的功能。

**建议**：`policy` 段增加 `require_human_signoff: true|false`（或按分支/项目粒度配置），默认给保守值；即便 MVP 硬编码为 `true`，也应在文档里显式声明这是刻意的默认值，而不是遗漏。

### 设计洞 4（P1）：与团队现有代码托管/PR 工作流的关系完全空白

**证据**：全文唯一出现 "GitHub"/"GitLab" 的地方是 §7.2 与业界对标的类比表（`MACAO_PRD_v2.md:1108-1121`，把 `REVIEW_REQUEST` 类比成"Manual Approval"），不是实际集成设计；"pull request""branch protection"等词全文未出现（已用 grep 核实）。§14.5 的合并目标是本地 `default_branch`，`macao.yaml` 只配置了 `remote_name`（`MACAO_PRD_v2.md:1290`）用于 `git fetch`，没有描述合并后是否/如何推送到远端、是否与远端已有的 PR 审核策略、必需状态检查（required status checks）、分支保护规则产生冲突。

**影响**：真实团队的代码仓库几乎必然托管在 GitHub/GitLab 一类平台并配有自己的 PR 审核与保护规则。MACAO 目前的设计像是在一个"本地专属副本"上运作一整套独立于宿主平台的评审/合并逻辑，一旦这个仓库需要推回团队共享的远端，MACAO 的自动合并与远端的分支保护/必需审核人策略如何共存是完全开放的问题。这不是无关紧要的边角案例，而是"产品本身是否可用"的核心前提之一。

**建议**：至少在边界声明中显式说明 MVP 阶段的假设——例如"仅面向未启用分支保护的本地/个人仓库，团队共享仓库的集成留待 v1.1"，避免用户在真实团队仓库上试用后才发现推送被拒绝或流程被绕开。

## 二、产品本身是否可用

### 对核心技术赌注的评估

产品能否成立，系于两个尚未验证的假设，文档自己也把其中一个列为头号风险：

1. **Claude Code Hook API 是否稳定可用**（`MACAO_PRD_v2.md:1156`，"CLI Hook API 不稳定｜中｜高"）——文档诚实地把这个不确定性列为最高风险项并安排 Week 1-2 PoC 验证，这是恰当的态度。
2. **Codex/Kimi 能否被 PTY 驱动，稳定产出 schema 合规的结构化 YAML**——这一点风险登记表里没有单独列出，但技术难度不比第一条低：`.review.yml` 是由 Reviewer CLI 自己"手写"生成的（`MACAO_PRD_v2.md:1009-1013`：`cat > .macao/.reviews/reviewer_id.review.yml <<EOF ... EOF`），而不是由 MACAO 侧的确定性代码序列化。通用编码 Agent 在自由文本生成中出现字段拼写错误、结构缺失是常见现象；一旦格式不合规，§2.2 的处理方式是"判为无效产物，不计入有效票"（`MACAO_PRD_v2.md:313`），**没有"提示 Reviewer 修正并在同一轮内重试"的机制**，只能等到超时/弃权流程把问题兜给人工。这意味着一次格式错误的代价是浪费一整轮评审窗口（默认 10 分钟/reviewer，见 `MACAO_PRD_v2.md:1309`），而不是几秒钟的重试。这是可用性上的真实摩擦点，建议在 PoC 阶段就加一个"格式校验失败 → 附带错误详情重新请求一次，仍失败才计为弃权"的短路径。

### 定位是否诚实、是否可信

§15.1 明确把 v2.x 定位为"固定三 CLI 的本地单机协作 **PoC 规格**"（`MACAO_PRD_v2.md:1371-1373`），不是通用平台；§15.5 给核心价值主张设了可证伪的验收线。这两点合起来说明：文档作者对"这东西现在到底有多大把握"是清醒的，没有过度承诺，这本身是"可用性"评估里的加分项——用户不会被误导为可以直接拿它替代团队现有的 code review 流程。

但当前的产品定义（执行摘要开篇，`EXECUTIVE_SUMMARY.md:11`）仍然写的是"把多个 CLI 工具组织成一个自动化的开发-评审-合并**团队**"，与 §14.2 "MVP 单机同一时刻仅允许一个活动任务（串行编排）"（`MACAO_PRD_v2.md:1350`）存在期望落差——"团队协作平台"的叙事与"任意时刻只能有一个任务在跑"的实际能力之间有明显落差，容易让第一次接触产品的人高估其并发/团队协作能力。建议要么在执行摘要开篇就注明"MVP 阶段是单任务流水线，'团队'体现在角色分工而非并发规模"，要么把开篇定义改得更保守。

### 结论

作为单个开发者在单台机器上、对可控范围的任务（2 小时内可完成、测试可自动跑）进行"AI 写代码 + 双 AI 复核"的实验性工具，当前设计是自洽、可实现的；但把它当作团队日常代码评审替代品来"可用"，现在还为时过早——不是因为文档写得不够，而是因为文档自己列出的两个核心风险（Hook API 稳定性、评审召回率 ≥60%）都还没有被验证。这个判断和文档的自我定位是一致的，属于健康的产品纪律，而不是设计缺陷。

## 三、技术设计是否完善

### 已经扎实的部分

- 状态识别改为"当前 FSM 状态 + checkpoint_ref/round"的作用域读取（`MACAO_PRD_v2.md:703-778`），并配了两个场景推演（`MACAO_PRD_v2.md:815-838`），有效解决了此前"旧产物遮蔽新状态"的问题，是本轮修订里质量最高的部分。
- `.review.yml` 原子写入约定（临时文件 + rename，`MACAO_PRD_v2.md:411`）正确处理了"MACAO 读取时 Reviewer 尚未写完"的竞态，这是容易被忽略但这里做对了的细节。
- 法定人数决策表（`MACAO_PRD_v2.md:398-409`）覆盖了 2/3 配置下的全部关键组合，是可执行的规范而非模糊描述。

### 仍不完善的部分

- **合并后失败处理**：见"一、设计洞 1"，`DONE` 状态与 CI Gate 失败后的返工路径矛盾，这是状态机层面尚未闭环的漏洞。
- **崩溃恢复算法**：`docs/reviews/2026-08-26-review-result-684a012-codex.md` 的 P1-3 已指出 State Store（SQLite）与 git 产物"双写、任一崩溃后可由二者重建"（`MACAO_PRD_v2.md:1220`）缺少事务顺序、序号和冲突判定算法。本次通读确认该问题在当前版本仍未关闭——正文只有一句结论性陈述，没有给出"SQLite 已写但 git 未提交"等具体场景的处理规则。这是全文本次审查中唯一采信自既有评审、但独立确认仍然成立的技术缺口，收录进本报告以保持问题清单完整。
- **测试策略未回答"如何测试一个依赖真实 LLM CLI 的非确定性系统"**：§4.1 P0 清单要求"单机编排的完整端到端测试"（`MACAO_PRD_v2.md:854`），§12.4 Adapter Conformance 给出了 producer→consumer fixture 校验（`MACAO_PRD_v2.md:1271-1277`，验证的是产物格式可解析），但没有涉及**行为层面**的端到端测试如何避免依赖真实 Claude Code / Codex / Kimi 进程带来的高成本、慢速度与非确定性（LLM 每次运行可能走不同路径、耗时不同）。建议在 §12.4 之外补一节"E2E 测试策略"，明确哪些层用真实 CLI 录制回放（VCR 式 fixture）、哪些层允许纯状态机单测覆盖，避免团队在实现阶段发现"测试怎么写"是空白。
- **Reviewer 执行权限边界**：见"一、设计洞 2"，这既是产品设计缺口，也是技术契约（Adapter Contract）层面应该有但没有的字段。

## 建议的下一步

1. 先关闭 F1、F2（P0）——两者都是"文档字面意思无法唯一确定系统行为"或"核心安全边界缺失"，性质上与此前几轮已关闭的 P0 同级，建议在启动 Week 1-2 PoC 编码前一并解决，避免 Adapter 实现按不完整契约编写后返工。
